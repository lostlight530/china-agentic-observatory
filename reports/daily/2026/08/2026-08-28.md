# Version Change Meets the Quality Gate / 版本变化进入质量门
## China AI Daily Research Report / 中国人工智能每日研究报告
### 2026-08-28

**Observation cut-off / 观察截止：2026-08-28 07:41 CST**

## 0｜Executive Judgment / 核心判断

W35 has progressively made the data-side correction loop more concrete:

```text
24 Aug  post-use evidence should return
25 Aug  feedback return becomes an operating function
26 Aug  evaluation diagnosis → targeted dataset optimization
27 Aug  optimization → version / provenance
```

Today adds the next governance boundary:

> **A changed dataset version should be treated as a new quality/governance state, not as automatic inheritance of the prior version's evaluation result**

The evidence does not yet establish a national mandatory re-evaluation rule

But several formal and implementation signals now align strongly enough to make the question explicit

### Formal workstreams

The 2026 first batch of national data-standard / technical-file needs includes, inside WG5:

- item 95 — `高质量数据集 认知价值评测要求`
- item 109 — `高质量数据集 版本管理与溯源技术要求`

Separately, the national standards platform already records:

- `20256913-T-907` — `高质量数据集 质量评测规范`, currently in consultation
- `20262581-Z-907` — `高质量数据集 质量评测系统技术要求`, currently drafting

These are separate projects

Their coexistence does **not** prove a formal version-to-re-evaluation crosswalk

But it creates strong structural pressure for quality evidence to become version-scoped

### Implementation case

A National Data Administration public case for a `数据锻造工厂` describes a high-quality data processing chain that includes both:

- quality evaluation
- version management

inside the same end-to-end processing pipeline

This is case-level implementation evidence that quality and version management can be operationally composed

It is not proof of nationwide interoperable lifecycle semantics

The Friday lifecycle therefore becomes:

```text
EVALUATION DIAGNOSIS
→ TARGETED OPTIMIZATION
→ DATASET CHANGE
→ NEW DATASET VERSION
→ VERSION / PROVENANCE RECORD
→ QUALITY / GOVERNANCE GATE
→ TRAINING / MODEL ITERATION
→ FOLLOW-UP EVALUATION
```

The key boundary is:

> **New dataset version ≠ inherited quality status**

No public source reviewed today establishes one machine-readable object binding the old evaluation result, optimization task, resulting dataset version, new quality result, later model version and follow-up evaluation

## 1｜Why this advances yesterday's version spine

Yesterday H10 established that version management and provenance are becoming explicit lifecycle infrastructure

But versioning alone can still degenerate into archival bookkeeping

For lifecycle correction to be governable, version change must affect what evidence is valid next

That means asking:

```text
quality_result(dataset_v1)
?
valid for dataset_v2
```

The safe default analytical answer is:

> **not automatically**

because data may have been recollected, relabeled, reweighted, synthesized, filtered or otherwise changed

The magnitude of change and mandatory re-evaluation conditions remain open policy / standards questions

## 2｜2026 work list — evaluation and version/provenance are both formal objects

The 2026 first-batch national data-standard needs list places multiple high-quality-dataset work items under WG5

Two are particularly important for W35:

```text
95  高质量数据集 认知价值评测要求
109 高质量数据集 版本管理与溯源技术要求
```

This is not an official linkage between the two

But it shows that `evaluation` and `version/provenance` are both being treated as explicit standardization / technical-file subjects

The observatory therefore upgrades the open question from:

> does version management exist?

to:

> can evaluation evidence be bound to an exact dataset version, and when must it be regenerated?

## 4｜Implementation case — quality evaluation and version management in one pipeline

The National Data Administration's public `数据锻造工厂` case describes an end-to-end high-quality data process

Its processing stage includes:

- format processing
- data cleaning
- synthetic augmentation
- data annotation
- quality evaluation
- version management

This matters because it is not merely policy vocabulary

It is a documented implementation pattern in which quality checking and version control coexist inside one operational data pipeline

### Boundary

The case does not publish:

- a national version identifier schema
- mandatory re-evaluation triggers
- evaluation-result expiry
- a standard before/after version diff format
- a common feedback-event ID
- a common data-work-item ID
- proof that every version change reruns all quality tests

So:

> **One pipeline composition ≠ national mandatory gate**

## 5｜Version-scoped quality evidence

The strongest analytical refinement today is to stop treating a quality report as an eternal property of a dataset name

A more auditable model is:

```text
dataset_id
├─ version v1
│  ├─ provenance
│  ├─ quality_result q1
│  └─ governance_status g1
│
└─ version v2
   ├─ change_reason / work_item
   ├─ provenance
   ├─ quality_result q2 ?
   └─ governance_status g2 ?
```

The `?` is the W35 gap

Version identity gives us the place where quality state can change, but does not itself prove that re-evaluation is mandatory or automatic

## 8｜The missing lifecycle object

The object is becoming increasingly specific:

```text
feedback_event_id
→ source application / scenario
→ model version
→ evaluation dataset + metric version
→ diagnosed gap
→ data_work_item_id
→ action / owner / approval
→ prior dataset version
→ resulting dataset version
→ provenance evidence
→ quality_result_id for resulting version
→ governance / rights status
→ later model version
→ follow-up evaluation result
```

This remains an observatory analytical model, not an official schema

The new field today is not merely `quality_result_id`

It is the requirement that the quality result be explicitly associated with the **resulting dataset version**
