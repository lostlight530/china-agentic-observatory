## 0｜Executive Judgment / 核心判断

W35 has progressively made the data-side correction loop more concrete:

```text
24 Aug  post-use evidence should return
25 Aug  feedback return becomes an operating function
26 Aug  evaluation diagnosis → targeted dataset optimization
27 Aug  optimization → version / provenance
28 Aug  new version → renewed quality / governance question
```

Today adds the next governance boundary:

> **A changed dataset version should be treated as a new quality/governance state, not as automatic inheritance of the prior version's evaluation result**

The evidence does not yet establish a national mandatory re-evaluation rule

But formal and implementation signals now align strongly enough to make version-scoped quality evidence a concrete W35 hypothesis

### Implementation case

A National Data Administration public `数据锻造工厂` case describes a high-quality data-processing chain that includes both:

- quality evaluation
- version management

inside the same end-to-end pipeline

This is case-level implementation evidence that quality and version management can be operationally composed

It is not proof of nationwide interoperable lifecycle semantics

The Friday lifecycle therefore becomes:

```text
EVALUATION DIAGNOSIS
→ TARGETED OPTIMIZATION
→ DATASET CHANGE
→ NEW DATASET VERSION
→ VERSION / PROVENANCE RECORD
→ QUALITY / GOVERNANCE GATE
→ TRAINING / MODEL ITERATION
→ FOLLOW-UP EVALUATION
```

The key boundary is:

> **New dataset version ≠ inherited quality status**

No public source reviewed today establishes one machine-readable object binding the old evaluation result, optimization task, resulting dataset version, new quality result, later model version and follow-up evaluation

## 1｜Why this advances yesterday's version spine

Yesterday H10 established that version management and provenance are becoming explicit lifecycle infrastructure

But versioning alone can remain archival bookkeeping

For lifecycle correction to be governable, a version transition must affect which evidence remains valid

The core question is:

```text
quality_result(dataset_v1)
?
valid for dataset_v2
```

The observatory's safe analytical default is:

> **not automatically**

because a new version may include recollection, relabeling, reweighting, synthesis, filtering, deduplication or other material changes

The magnitude of change and mandatory re-evaluation conditions remain open standards and governance questions

## 2｜WG5 — evaluation and version/provenance are both explicit work objects

The 2026 first-batch work list places multiple high-quality-dataset items under WG5

Two are central to today's question:

```text
95  高质量数据集 认知价值评测要求
109 高质量数据集 版本管理与溯源技术要求
```

This is not an official linkage between the two

It does show that both evaluation and version/provenance are explicit standardization subjects

The research question therefore moves from:

> does version management exist?

to:

> can an evaluation result be bound to an exact dataset version, and when must that result be renewed?

## 4｜Implementation case — quality evaluation and version management in one pipeline

The National Data Administration's public `数据锻造工厂` case shows one high-quality-data processing chain containing:

- format processing
- data cleaning
- synthetic augmentation
- data annotation
- quality evaluation
- version management

This matters because it is an implementation pattern rather than only policy vocabulary

### Boundary

The case does not publish:

- a national version identifier schema
- mandatory re-evaluation triggers
- evaluation-result expiry / supersession rules
- a standard before/after version-diff format
- a common feedback-event ID
- a common data-work-item ID
- proof that every version change reruns every quality test

Therefore:

> **One pipeline composition ≠ national mandatory quality gate**

## 5｜Version-scoped quality evidence

A quality report should not be treated as an eternal property of a dataset name

A more auditable model is:

```text
dataset_id
├─ version v1
│  ├─ provenance
│  ├─ quality_result q1
│  └─ governance_status g1
│
└─ version v2
   ├─ change_reason / work_item
   ├─ provenance
   ├─ quality_result q2 ?
   └─ governance_status g2 ?
```

The question marks are the W35 gap

Version identity provides the place where quality state can change, but does not itself prove that re-evaluation is mandatory or automatic

## 8｜The missing lifecycle object

The object is becoming increasingly specific:

```text
feedback_event_id
→ source application / scenario
→ model version
→ evaluation dataset + metric version
→ diagnosed gap
→ data_work_item_id
→ action / owner / approval
→ prior dataset version
→ resulting dataset version
→ provenance evidence
→ quality_result_id for resulting version
→ governance / rights status
→ later model version
→ follow-up evaluation result
```

This remains an observatory analytical model, not an official schema

The new requirement today is not merely `quality_result_id`

It is that the quality result be explicitly associated with the **resulting dataset version**
