# Lifecycle Correction / 生命周期纠偏
## China AI Weekly Research — 2026-W35 Progress
### Watch window: 2026-08-24 → 2026-08-30
### Updated: 2026-08-27

> **From Governable Feedback to Lifecycle Correction**  
> **从可治理反馈，走向生命周期纠偏**

## 0｜Current Weekly Judgment / 当前周度判断

W35 asks whether post-use evidence can change later dataset, access, credential or model state

Four days now reveal an increasingly explicit data-side lifecycle

```text
24 Aug  post-use evidence should return
25 Aug  feedback return becomes an operating function
26 Aug  evaluation diagnosis → targeted dataset optimization
27 Aug  optimization → dataset version / provenance → later re-evaluation
```

The emerging model is:

```text
APPLICATION / OPERATION
→ FEEDBACK
→ EVALUATION / DIAGNOSIS
→ TARGETED DATASET OPTIMIZATION
→ VERSIONED DATASET CHANGE
→ PROVENANCE / TRACEABILITY
→ QUALITY + GOVERNANCE RE-EVALUATION
→ MODEL ITERATION
→ FOLLOW-UP EVALUATION
```

The new judgment is:

> **Version management and provenance are becoming explicit lifecycle infrastructure**

But:

> **Version lineage ≠ feedback-event / work-item lineage**

## 1｜W35 Hypothesis Progress / 假设进展

### H1 — Post-use evidence becomes a formal feedback input

**STRONGLY STRENGTHENED**

Policy, implementation cases and evaluation-driven optimization all support later use of application / evaluation evidence

### H2 — Application evidence triggers explicit data work

**STRONGLY STRENGTHENED / REFINED**

W35 has progressed from automatic return and targeted supplementation to a formal `evaluation diagnosis → targeted optimization` direction

**Open edge:** no common auditable data-work-item object is public

### H3 — Feedback reuse requires provenance and quality gating

**STRONGLY STRENGTHENED**

A dedicated version/provenance work-item signal increases pressure to preserve what data changed before reuse

Quality/governance admission remains distinct from version creation

### H4 — Quality evidence and usage-control evidence require a formal crosswalk

**OPEN**

Version/provenance does not yet map quality reports, dataset credentials, contracts, usage-control strategy IDs and fulfillment evidence into one lifecycle

### H5 — Termination and violation affect credential/access state

**OPEN**

Today's evidence concerns dataset lifecycle memory rather than access-state revocation

### H6 — Derived outputs inherit governance questions

**OPEN**

No new formal evidence establishes restriction inheritance into derived datasets, models, embeddings or Agent outputs

### H7 — Cross-system lifecycle mapping becomes necessary

**STRONGLY STRENGTHENED**

Version/provenance now adds a stable state-reference requirement between evaluation, dataset operations, model iteration and later validation

### H8 — Feedback return becomes an explicit operating function

**STRONG MULTI-CASE IMPLEMENTATION SIGNAL**

Public cases continue to show return as a real platform/data-operation capability

### H9 — Evaluation diagnosis becomes explicit dataset-optimization backpressure

## 6｜The Missing Lifecycle Object / 仍缺失的生命周期对象

The model is now more specific:

```text
feedback_event_id
→ source application / scenario
→ model version
→ evaluation dataset + metric version
→ diagnosed gap
→ data_work_item_id
→ action / owner / approval
→ prior dataset version
→ resulting dataset version
→ provenance evidence
→ later model version
→ follow-up evaluation result
```

Three identifiers must remain distinct:

```text
feedback-event ID ≠ data-work-item ID ≠ dataset-version ID
```

## 7｜Research Priorities / 本周优先问题

1. Does the version/provenance work item publish concrete metadata / identifier fields?
2. Can evaluation diagnosis reference an exact prior dataset version?
3. Can a data-work item reference both diagnosis and resulting dataset version?
4. Can quality evaluation be repeated automatically or mandatorily after version change?
5. Can model version / evaluation result close the prior optimization task?
6. Can platform credentials and trusted-data-space contracts reference dataset-version lineage?
7. Can derivatives preserve source-version restrictions?
8. Can public cases expose version diffs and task-level audit evidence?

## 8｜Evidence Discipline / 证据纪律

```text
planned technical file ≠ published technical file
version management ≠ causal feedback linkage
traceability ≠ automatic quality approval
new dataset version ≠ automatic training admission
version ID ≠ work-item ID

provenance evidence ≠ proof that optimization improved the model
```
